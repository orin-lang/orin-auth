# Annotations

orin-web's annotation layer (`@Controller`, `@Get`, `@Use`, ...; PR orin-lang/orin-web#1) has three limits that decide what orin-auth can
offer (docs/compiler-issues.md of orin-web): annotations cannot target parameters, generated code cannot write `new`, and a processor
only sees declarations that carry its own annotation. So orin-auth does not define annotation records of its own (nothing would read
them); it uses what orin-web already reads: `@Use("name, other")`, which looks the names up in the `Middlewares` registry.

```ts
@Controller("/projects")
@Use("authenticated")                      // every route of the controller needs a principal (@Auth is the same)
export class ProjectController {
  @Get("/")
  list(): Project[] { ... }

  @Post("/:id/deploy")
  @Use("scope:deploy")                     // this route also needs the scope "deploy"
  deploy(id: int, req: Request): Result<Response, WebError> {
    const me = currentPrincipal(req)?;     // the injected principal: the Request parameter is bound by orin-web
    ...
  }

  @Delete("/:id")
  @Use("role:admin")
  remove(id: int): Result<void, WebError> { ... }
}
```

Wiring, once, where the application is built:

```ts
const mws = authMiddlewares(newMiddlewares().with("log", logger(sink)), mixedAuthzConfig("/login"), ["admin", "ops"], ["deploy"]);
const app = buildApp(deps, mws);      // generated by @Application
app.use(authenticate([...], now));    // global: runs before the named middleware
```

`authMiddlewares` registers `authenticated` and `auth`, `role:<r>` for each role in the list and `scope:<s>` for each scope in the list.
Only declared roles and scopes exist, so `@Use("role:adnim")` stops the program at start-up (orin-web: exit 101, naming controller,
method and middleware) instead of protecting nothing. Names listed together are all required, the first is the outermost.
`tests/annotated_test.or` runs exactly the call the generated code makes (`useAll`).

## What orin-auth would need from orin-web / std:meta

1. **A `Principal` parameter.** With parameter annotations (orin-web compiler-issues P2), or with a rule that binds a parameter by its TYPE,
   `deploy(id: int, me: Principal)` would work. The convention to adopt: a type may provide `static fromRequest(req: Request):
   Result<T, WebError>`, and the generated handler calls it for an otherwise unbound parameter of that type. orin-auth would
   provide `Principal.fromRequest` (today's `currentPrincipal`). Until then take a `Request` and call `currentPrincipal(req)?`.
2. **Parameterised middleware names.** `@Use("role:admin")` works because orin-auth registers every name in advance. With
   `@Use("role", "admin")` (a middleware factory taking the annotation's constants) there would be no registry to keep in step.
3. **Importing a processor package that depends on orin-web.** An application that lists orin-web next to orin-auth gets two
   incompatible copies of orin-web (see security.md, "Known limits"), so `[annotations] processors = ["orin-web"]` and the
   re-exports of orin-auth cannot yet be used together; the generated companion modules name orin-web types.
